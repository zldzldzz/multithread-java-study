### 멀티 스레드 환경과 하나의 DB에 다중 트랜잭션 상황의 동시성 문제

이번에 멀티 스레드 환경에서의 동시성을 공부하면서 DB에서의 동시성 문제와 문제 상황의 유사성이 보였습니다.  

DB에서 하나의 레코드에 대해 여러 트랜잭션이 들어왔을 때,  
이 데이터를 어떻게 할 것인가? 에 대한 점괴
하나의 자원에 대해 여러 스레드가 접근할 때 어떻게 처리할 것인가? 에 대한 점에서 유사하게 느껴졌습니다.  

이번에는 각각 OS와 DB의 동시성 문제 상황을 정리하고,  
이를 해결하는 해결책을 정리하면서 공통점과 차이점에 대해 정리해보겠습니다.

---

#### 다중 트랜잭션에서의 동시성 문제

##### 문제 상황

DB에서는 여러 트랜잭션이 동시에 하나의 데이터를 읽거나 수정하는 상황이 발생할 수 있어서 다음의 문제가 생길 수 있습니다.

- ditry read : 아직 커밋되지 않은트랜잭션의 변경 내용을 다른 트랜잭션이 읽어 버리는 상황
- non repeatable read : 한 트랜잭션 안에서 같은 조건으로 두 번 select 했을 때 그 사이 다른 트랜잭션이 데이터를 변경해 두 번째 조회 결과가 달라지는 상황
- phantom read : 한 트랜잭션 안에서 같은 조건으로 두 번 select 했을 때, 그 사이 다른 트랜잭션이 새로운 행을 변경해서 두 번째 조회 시 “행의 집합 자체”가 달라지는 상황

##### 해결책

###### @Transactional 
스프링에서 메서드나 클래스에 이 어노테이션을 붙이면, 
트랜잭션 시작–커밋–롤백을 자동 관리해 DB가 제공하는 트랜잭션 격리 수준을 적용시켜서 격리 수준을 높입니다.    

하지만, 격리 수준이 높아질수록 동시 처리량이 떨어져서 성능이 저하됩니다.

###### 비관적 락
데이터에 잠금을 걸어 다른 트랜잭션의 접근을 차단함으로 충돌을 해결합니다.  

하지만, 락 경합으로 대기 시간이 길어져서 성능이 저하될 수 있습니다.

###### 낙관적 락
락을 걸지 않고 버전 비교로 커밋 시점에 충돌을 감지함으로 동시 처리를 합니다.  

하지만, 충돌 시 재시도를 하게 되서 갱신 빈도가 높은 환경에서는 충돌이 빈번해져서 실행이 지체됩니다.

---

#### 멀티 스레드 환경의 동시성 문제

##### 문제 상황

JVM 내에서 여러 스레드가 같은 메모리 자원에 동시에 접근할 때 다음과 같은 문제가 발생합니다.

- Race Condition : 두 스레드가 동시에 값을 갱신해 값이 꼬이는 현상
- Deadlock : 서로가 상대가 가진 락을 기다리다 무한 대기하는 상황
- Memory Visibility 문제 : 한 스레드의 변경 사항이 다른 스레드에 바로 보이지 않는 현상

##### 해결책

###### @Synchronized  
특정 메서드나 블록에 모니터 락을 걸어 한 시점에 한 스레드만 접근함으로 스레드 충돌을 피합니다.  

하지만, 락 경합이 심해지면 빈번한 스레드 교체로 인한 컨텍스트 스위칭 증가로 성능이 저하될 수 있습니다.

###### volatile 키워드
스레드에 캐싱을 하지 않음으로 변수 값에 가시성을 보장해 캐싱 일관성 문제를 해결합니다.  

하지만, 캐싱을 하지 않음으로 직접 메모리에 접근해야 해서 시간이 늘어남으로 성능이 저하되고,  
읽기만 가능하므로 원자성은 보장하지 않아 복합 연산에는 부적합합니다.

###### Lock/Condition 객체
스레드에 세밀한 락 제어, 조건 대기/알림 등 고급 동기화 제공해서 데드락 상태를 해결합니다.  

---

#### 두 문제의 관련성

##### 공통점

2가지 문제 모두 발생 원인이 접근자(스레드, 트랜잭션)가 공유 데이터에 동시에 접근함으로 데이터의 무결성을 해침으로 발생한 문제입니다.  

이를 해결하기 위해 2가지 모두 'LOCK'으로 데이터를 잠가서 하나씩 접근할 수 있도록 하고 있습니다.

##### 차이점

DB는 트랜잭션 매니저가 제공하는 격리 수준(READ COMMITTED, SERIALIZABLE 등)을 조정해 동시성 제어와 처리 성능 사이에서 균형을 잡습니다.  

반면 OS/JVM의 멀티스레드 환경은 개발자가 synchronized, Lock, CAS 등 직접 동기화 기법을 선택·구현해야 하며,  
필요에 따라 여러 스레드를 병렬로 돌리거나 락을 최소화하는 전략도 씀으로 개발자 역량에 달려 있는 것 같습니다.

---

### 결론

동시성이라는 같은 주제의 문제에서 OS와 DB가 어떻게 해결하는지를 정리해봤습니다.  
DB는 요청자에게 데이터를 보내줘야하므로 안전함보다는 동시 처리에 조금 더 신경쓰는 듯한 느낌을 받았습니다.  
하지만 OS는 서버의 자원을 다루므로 동시 처리보다는 무결하게 최대한 안전함을 신경쓰는 느낌을 받았습니다.  

한 문제에 대해 두 분야가 어떻게 해결하는지를 봄으로 각 CS 분야의 추구하는 바를 더 정리해볼 수 있었습니다.
