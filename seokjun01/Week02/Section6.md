# 📚 2주차 - 섹션 6

### 📚 메모리 가시성 (Memory Visibility)

## 1. 메모리 가시성 문제

**메모리 가시성(Memory Visibility)**은 멀티스레드 환경에서 한 스레드가 변경한 값이 다른 스레드에게 언제 보이는지에 대한 문제. 우리가 예상한 대로 프로그램이 동작하지 않는 주된 이유는 바로 캐시 메모리 때문.

### 왜 우리가 예상한 대로 동작하지 않았을까?

CPU는 처리 성능을 높이기 위해 캐시 메모리를 사용. 대부분의 CPU 코어는 자체적인 캐시 메모리를 가지고 있으며, CPU 연산의 빠른 속도를 따라가기 위해 메인 메모리보다 훨씬 빠름.

* 문제 발생: MyTask의 runFlag가 true일 때, Work 스레드는 이 값을 자신의 CPU 캐시 메모리로 가져와 사용.
* 값 변경의 지연: 메인 스레드가 runFlag를 false로 바꾸면, 이 변경은 먼저 메인 스레드가 사용하는 CPU의 캐시 메모리에만 반영. 메인 메모리에는 즉시 반영되지 않음.
* 불일치: Work 스레드는 여전히 자신의 캐시 메모리에 있는 true 값을 계속 사용하기 때문에, while 루프를 빠져나오지 못하게 되지.

캐시 메모리에 있는 값이 언제 메인 메모리에 기록될지, 그리고 다른 스레드의 캐시 메모리로 언제 갱신될지는 보장되지 않음. 주로 컨텍스트 스위칭이 일어날 때 갱신되긴 하지만, 보장된 동작은 아님.

## 2. Volatile 키워드

메모리 가시성 문제를 해결하고, 변경 사항이 즉시 다른 스레드에 반영되도록 하는 간단한 방법이 있어. 바로 volatile 키워드를 사용하는 것.

volatile 키워드가 붙은 변수는 항상 메인 메모리에서만 읽고 쓰기를 수행.
캐시 메모리를 사용하지 않기 때문에, 여러 스레드에서 같은 값을 읽고 쓸 때 값의 불일치 문제를 방지할 수 있음.
이건 약간의 성능 저하를 감수하는 대신 정확성을 보장하는 방법.
여러 스레드에서 같은 값을 읽고 써야 할 때 필수적으로 사용돼.

## 3. 자바 메모리 모델 (Java Memory Model, JMM)

JMM은 자바 프로그램이 메모리에 어떻게 접근하고 수정할 수 있는지를 규정하는 모델.
특히 멀티스레드 프로그래밍에서 스레드 간의 상호작용을 정의하지.

JMM의 핵심 원리 중 하나는 happens-before 관계야.

* happens-before: A 작업이 B 작업보다 happens-before 관계에 있다면, A에서 발생한 모든 변경 내용은 B가 시작되기 전에 이미 완벽하게 반영되어 있음을 보장.

volatile 키워드는 이런 happens-before 관계를 확립해주는 역할을 해. volatile 변수에 대한 쓰기 작업은 해당 변수에 대한 모든 읽기 작업보다 happens-before 관계를 보장하며, 이를 통해 메모리 가시성 문제가 해결.
