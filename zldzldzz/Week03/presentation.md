# wait/notify 올바른 패턴과 Spurious Wakeup
두 스레드가 버퍼(Buffer)라는 저장 공간을 사이에 두고 협력하는 상황 이때 특정 조건일때의 잠든 상태와 깨어있는 상태를 담당하는 것이 `wait()` 와`notify()`입니다.
## 핵심 규칙: wait()은 반드시 while 안에 넣어야 한다.
### 잘못된 패턴
```java
if (조건이 거짓) {
    lock.wait(); // 잠든다
}
// 깨어난 후 바로 진행
```
### 올바른 패턴
```java
while (조건이 거짓) {
    lock.wait(); // 잠든다
}
// while 루프를 통과했다면, 조건이 참! 안전하게 진행
```
`wait()` 메서드는 항상 `while (조건이 거짓) { wait(); }`로 감싸야 합니다. (이 패턴을 `보호된 블록(Guarded Block)`이라고 부릅니다.)

## 왜 WHILE 문으로 재확인해야 하는가? (필수 이유 3가지)

### 1.  허위 깨움 (Spurious Wakeup) 문제

- **현상:** `notify()`, `interrupt()` 같은 깨우는 신호가 **전혀 없었음**에도 불구하고, OS나 JVM의 내부적인 이유로 스레드가 가끔 잠에서 깨어날 수 있습니다.
- **결론:** 스레드가 깨어났다면, 일단 `while` 문으로 가서 **"내가 원하는 조건이 정말 충족됐는지"** 다시 확인해야 합니다. 만약 조건이 여전히 거짓이면 다시 `wait()`으로 돌아가 잠들어야 안전합니다.

### 2. 락 경쟁에 의한 조건 변동

- **상황:** `notifyAll()`이 A, B, C 세 스레드를 한 번에 깨웠습니다.
- **문제:**
    1. 세 스레드는 깨어난 후 락(Lock)을 다시 차지하기 위해 경쟁합니다.
    2. **A 스레드**가 가장 먼저 락을 얻고, 원하는 작업을 모두 처리했습니다.
    3. A 스레드가 락을 풀자마자, **B 스레드**가 락을 얻습니다.
    4. B 스레드가 확인해보니, A 스레드가 작업을 끝내버려 **조건이 다시 깨져있는** 상태입니다 (예: 버퍼가 다시 비어버림).
- **결론:** 깨어났을 당시의 조건과 락을 실제로 획득한 순간의 조건은 다를 수 있습니다. `while` 문은 B 스레드에게 "너의 조건이 만족되지 않았으니 다시 잠들어"라고 알려줍니다.

### 3. 잘못된 대상 깨움 (단일 대기실 문제)

- **상황:**
    - 소비자 스레드(버퍼 비었을 때 대기)
    - 생산자 스레드(버퍼 가득 찼을 때 대기)
    - 이 둘은 하나의 대기실(Wait Set)에서 함께 기다립니다.
- **문제:** 버퍼에 아이템 1개가 추가되어 **소비자만 진행 가능한 상황**입니다. 그런데 누군가 `notify()`를 호출했는데, **엉뚱하게 생산자가 깨어나는** 경우가 생길 수 있습니다.
- **결론:** 잘못 깨어난 생산자는 `while` 문을 통해 "버퍼가 아직 가득 차지 않았네? (내 조건이 거짓이네?)"를 확인하고 **다시 잠들어야 합니다.** 만약 `if` 문이었다면 잘못된 조건으로 진행해 버리는 심각한 오류(데드락 등)가 발생할 수 있습니다.

## 올바른 패턴 (Guarded Block)

`wait`/`notify`는 항상 **`synchronized` 블록 안에서** 사용해야 합니다.

**소비자 (비어있으면 기다림)**
```java
public Object take() throws InterruptedException {
    synchronized (lock) { // 1. 락(자물쇠)을 잠근다
        while (count == 0) { // 2. `가드 재확인` 버퍼가 비었으면 반복
            lock.wait(); // 3. 대기: 락을 반납하고 잠든다
        }
        // 4. 조건 성립-> 안전하게 아이템을 꺼낸다 (count--)
        
        lock.notifyAll(); // 5. (깨움) 상태가 변했음을 모두에게 알린다
        return item;
    } // 6. 락을 푼다
}
```

## `notify()` vs `notifyAll()`: 무엇을 쓸까?

어떤 스레드를 깨울지 선택하는 문제입니다.

|  | 깨우는 스레드 수	 | 사용 원칙 (초보자 권장) |
| --- | --- | --- |
| `notify()` | **딱 1개** (JVM이 임의로 선택) | **가급적 쓰지 마세요** (복잡함) |
| `notifyAll()` | **모두 다** 깨운다 | 기본적으로 이것을 쓰세요 |

### **`notifyAll()`을 기본으로 권장하는 이유**

`notify()`를 썼을 때, 진행 가능한 스레드가 아닌 **엉뚱한 스레드를 깨우면** 시스템 전체가 멈추는 **교착 상태(Deadlock)**에 빠질 위험이 있습니다.

`notifyAll()`은 대기실의 **모든 스레드를 깨웁니다.**

- 모두 깨어나 락을 얻기 위해 경쟁합니다.
- 깨어난 스레드는 `while` 문으로 가서 "내 조건이 만족됐나?"를 스스로 확인합니다.
- **진짜 진행 가능한 스레드**만 `while` 문을 빠져나와 작업을 수행하고, **나머지 스레드**는 다시 `wait()`으로 돌아가 안전하게 잠듭니다.

결론: notifyAll()이 notify()보다 아주 조금 더 느릴 수 있지만, 정확성과 안전성(Deadlock 방지) 면에서 압도적으로 우수하므로, 특별한 이유가 없다면 notifyAll()을 사용하는 것이 좋다고 생각합니다.
