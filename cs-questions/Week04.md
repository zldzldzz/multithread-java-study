# 4주차

석준 Q : Synchronized 동기화를 사용하는 것 보다 CAS연산(스핀 락)을 통해 최적화를 하는게 더 나은 경우는 어떤 경우인가요?

석준 A : 스레드가 `RUNNABLE` → `BLOCKED` , `WAITING` 상태에서 다시 `RUNNABLE` 상태로 가는 것 보다는, 스레드를 `RUNNABLE` 로 살려둔 상태에서 계속 락 획득을 반복 체크하는 것이 더 효율적인 경우에 사용해야한다. 

---

**준선 Q: ConcurrentHashMap과 HashMap의 차이는 무엇인가요?**

HashMap은 스레드에 안전하지 않은 일반적인 Map 구현체입니다.

여러 스레드가 동시에 수정 작업을 수행하면데이터 불일치 문제가 발생할 수 있습니다.

반면 ConcurrentHashMap은 멀티 스레드 환경에서도 안전하게 동작합니다.

**준선 Q : 그럼  ConcurrentHashMap이 어떻게 멀티 스레드 환경에서도 안전하게 동작하나요?**

ConcurrentHashMap은 노드 단위로 synchronized와 CAS를 이용해 여러 스레드가 동시에 다른 버킷을 수정해도 안전하게 동작합니다. 

단순 읽기 연산은 락 없이 수행되고, 쓰기만 필요한 부분에 락을 수행합니다.

---

채연 Q: CAS와 락 방식을 비교하고, 어떤 경우에 CAS 방식을 사용하는 것이 유리한지 알려주세요.

채연 A:

[CAS 방식]

- 락을 사용하지 않음
- 1000개의 스레드를 가정하면, 모든 스레드가 한 번에 실행
- 충돌 나는 경우만 재실행

[락 방식]

- 데이터 접근 전에, 항상 락 획득
- 1000개의 스레드를 가정하면, 각 스레드 모두 락을 획득하고 반환하는 과정
- 각 스레드가 순서대로 하나씩 실행

⇒ 간단한 CPU 연산에는 락보다 CAS 방식이 유리함. (간단한 CPU 연산은 스레드 간 충돌이 적기 때문)

규민 Q : 동시성 컬렉션같은 동시성이 보장된 자료구조를 구현하기 위해서는 무엇을 고려해야하나요?

규민 A: 

동시성이 보장된 자료구조를 구현하려면 동시성과 성능 사이의 균형을 고려하며 설계해야 합니다.

동시성을 우선시하면, 세밀한 락이나 CAS 같은 원자 연산으로 일관성을 보장하지만 락 경합으로 성능이 떨어질 수 있습니다. 

성능을 우선시하면, 락을 줄이거나 약한 동시성을 허용해 처리 속도를 높이지만, 일시적 불일치나 최신 데이터 반영 지연이 생길 수 있습니다.

원진 Q: CAS 성공/실패 케이스를 값 변화 순서로 설명해 보세요

원진 A: 

`AtomicInteger` 객체의 내부 값(`value`)이 **0**이라고 가정합니다.

성공: 

- 단일 스레드 또는 다른 스레드의 간섭이 없는 상황에서 연산이 성공하는 경우입니다.
    - 초기 상태: `value`는 0입니다.
    - 연산 호출: `compareAndSet(0, 1)`을 호출합니다. (기대 값: 0, 새로운 값: 1)
    - 비교 및 교체: 현재 `value`(0)와 기대 값(0)을 비교합니다. 일치하므로 하드웨어 수준에서 원자적으로 `value`를 새로운 값인 1로 교체합니다.
    - 결과: 최종 `value`는 1이 되고, 연산은 `true`를 반환합니다.

실패:

- 멀티스레드 환경에서 다른 스레드가 값을 먼저 변경하여 기대 값과 현재 값이 달라진 경우입니다.
    - 초기 상태: `value`는 0입니다.
    - 동시 접근: 스레드 A와 스레드 B가 모두 `value`가 0임을 확인하고, 값을 1로 증가시키려고 합니다.
    - 스레드 B 선점: 스레드 B가 먼저 CPU를 점유하여 `compareAndSet(0, 1)`을 실행합니다. `value`가 기대 값(0)과 일치하므로 연산에 성공하고, `value`는 1이 됩니다.
    - 스레드 A 시도: 직후 스레드 A가 `compareAndSet(0, 1)`을 실행합니다.
    - 비교 실패: 현재 `value`(1)가 스레드 A의 기대 값(0)과 불일치하므로, 값을 교체하지 않습니다.
    - 결과: `value`는 1로 유지되고, 연산은 `false`를 반환합니다.

기민Q: 프록시 패턴은 무엇이고 장단점을 설명하시오.

기민A:

프록시 패턴: 대리자 객체를 만들어, 실제 객체에 접근하기 전/후로 추가 로직을 수행하는 디자인 패턴

장점

1. 접근 제어 - 클라이언트가 직접 설계 객체에 접근하지 않게 하여, 보안이나 권한 검사를 추가할 수 있다.
2. 지연 초기화(Lazy Loading) - 객체 생성 비용이 큰 경우, 실제 필요할 때 생성하도록 최적화할 수 있다.

단점

1. 성능 저하 가능성 - 요청이 실제 객체로 전달되기 전에 프록시 단계를 거치기 때문에 오버헤드가 발생할 수 있다.
2. 구조 복잡도 증가 - 프록시 객체가 추가되므로 클래스 수가 늘어나고 유지보수가 복잡해진다.
