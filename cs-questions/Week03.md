**원진 Q:** `synchronized` 와 `ReentrantLock`  중에 사용한다면 어떤 것을 사용하고 그 이유는 무엇인가요?

**원진 A:** 

**단순 임계구역**(짧은 구간, 추가 제어 불필요)이라면 **`synchronized`** 을

**대기 제어(취소·타임아웃) / 공정성 / 다중 조건변수**가 필요하면 **`ReentrantLock`** 을 사용할 것 같습니다.

- 자세히 보기
    
    `synchronized`를 선택한다면?
    
    간결하고 안전하다: 블록/메서드 스코프 탈출(예외 포함) 시 자동으로 해제된다.
    재진입·가시성: 모니터 enter/exit 시 happens-before가 형성되어 메모리 일관성이 확보된다.
    오버헤드 최소화: 단순 임계구역에서는 가장 읽기 쉽고 최적화 여지가 크다.
    
    한계: 락 획득 대기 중 인터럽트로 깰 수 없고 타임아웃 없다. 모니터에는 단 하나의 조건 큐만 있어 wait/notify 사용 시 while 재검증과 notifyAll 선택 등 신호 설계가 번거로울 수 있다.
    
    `ReentrantLock`을 선택한다면?
    
    대기 제어가 필요하다:
    lockInterruptibly() → 대기 중 취소/중단 가능
    tryLock(timeout) → 지연 제한으로 교착·장기대기 완화
    공정성 옵션: new ReentrantLock(true)로 선입선출에 가까운 깨어남을 유도 하지만 처리량은 떨어질 수 있다.
    다중 조건변수: Condition을 여러 개 두어 신호를 목적지에만 보낸다.
    명시적 프로토콜: await()/signal()은 반드시 락을 쥔 상태에서 호출한다. 깨운 뒤엔 while로 조건 재확인된다.
    
    주의: unlock() 누락 위험이 있어 반드시 try/finally 패턴으로 감싸야 한다.

규민 Q : 자바에서 wait()과 notify() 메서드는 어떻게 작동하나요?

규민 A:   wait()은 현재 스레드가 객체의 모니터 락을 가지고 있을 때 호출되면, 그 락을 풀고 해당 객체가 대기 상태로 들어가서 다른 스레드가 깨워줄 때까지 멈춰 있게 됩니다.

반대로 notify()는 같은 객체의 모니터에서 대기 중인 스레드 중 하나를 깨우지만, 바로 실행되는 게 아니라 현재 락을 가진 스레드가 종료되어 락을 반환해야만 깨어난 스레드가 다시 실행을 이어갈 수 있습니다.

채연 Q: synchrozied 환경에서, `sleep()`과 `wait()`의 차이는 무엇인가요?

채연A: 

- `sleep()`은 `Thread`의 메서드로, **락을 쥔 상태 그대로 일정 시간 동안 스레드를 멈추게** 합니다. 시간이 지나거나 `interrupt()`가 호출되면 깨어납니다.
- `wait()`은 `Object`의 메서드로, 반드시 `synchronized` 블록 안에서 호출해야 하며, **락을 반납하고 대기 상태**에 들어갑니다. 이후 같은 객체에서 `notify()` / `notifyAll()` (또는 `interrupt()`) 호출로 깨어납니다.

기민 Q: synchronized와 LockSupport.park()의 차이점은 무엇인가요?

|            | synchronized                                                     | LockSupport.park()                               |
| ---------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 상태         | BLOCKED (모니터 락 획득 대기 시)<br>TIMED_WAITING / WAITING (wait() 호출 시) | WAITING / TIMED_WAITING                          |
| 스레드 제어     | 불가능 (스케줄러가 알아서 스케줄링함)                                            | 가능 (직접 스레드를 parking 상태로 만들고, unparking 할 수 있음)   |
| 락/임계 구역 보호 | 진입 시 자동 락 획득<br>해제 시 happens-before 보장 (메모리 가시성 확보)              | 락 개념 없음<br>스레드 정지/재개만 제공<br>메모리 가시성 보장 x         |
| 인터럽트 반응    | 락 획득 대기 중 인터럽트 불가능 ( wait() 호출 중에는 InterruptedException 발생)      | 인터럽트 가능 (예외 없이 그냥 깨어나기만 함, 인터럽트 플래그는 true로 남아있음) |
